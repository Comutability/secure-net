## 1. Problem

Messages today are sealed to an account's key, which every device of the account shares
(`crypto/envelope`, `crypto/keyring`). That has three gaps:

1. **No forward secrecy.** Anyone who gets that key, from any device at any time, can read every
   message ever sealed to it, including recordings.
2. **Not fully post-quantum.** The envelope uses P-256 and ML-KEM-768 together, but keeps a
   classical-only fallback, and device and account signatures are classical ECDSA P-256.
3. **No clean, reusable session API.** Apps can't easily build correct end-to-end messaging on
   Secure Net.

## 2. Proposed change

Add CVP-016 and `src/session/`:

- Account keys and device keys signed with Ed25519 + ML-DSA-65; a signed, monotonically
  numbered device list; signed X25519 and ML-KEM-768 prekeys, one-time and last-resort.
- A handshake combining three or four X25519 agreements with ML-KEM-768, bound to a transcript of
  both parties' keys (in the style of Signal's PQXDH).
- A double ratchet in which every DH step also mixes in a fresh ML-KEM-768 secret, and refuses
  new chains that leave it out.
- Per-device fan-out, sender-key groups with rekeying when members leave, and history moved to a
  new device end to end after the person compares link codes.
- Test vectors, conformance tests and a runnable example.
- Feature `cvp.sessions` version 1; Secure Net 0.4.0.

## 3. Benefits and intended uses

Any app built on Secure Net, Commonveil first, gets messaging whose content stays private from
every site and network in between, now and against a future quantum computer, with forward
secrecy and recovery after a device compromise. People get safety numbers to check each other
and a way to add a device without a site ever holding their history.

## 4. Security and privacy

See CVP-016, "What it protects" and "What isn't protected". In short: confidentiality rests on
X25519 **and** ML-KEM-768 together; signatures on keys are Ed25519 **and** ML-DSA-65; group
messages are signed with Ed25519 only (stated, with the reason); metadata is still visible to
sites; first contact needs safety-number comparison.

This is security-critical cryptographic code written by an AI. Under GOVERNANCE.md it needs a
qualified human reviewer before it moves past Technical Review, and nothing should rely on it
until then. Points that most need a reviewer's eye:

- the handshake transcript and the key schedule (KDF inputs, labels, ordering);
- the ML-KEM ratchet step and the downgrade rule;
- skipped-key limits and state handling on failure;
- the trust model for device lists (who holds the account key) and the link code length;
- that every one-time prekey really is used once, on the server side too.

## 5. Compatibility

Nothing existing changes: `crypto/envelope` and the other modules keep working, and sites that
don't announce `cvp.sessions` are unaffected. Apps adopt it explicitly. Messages in the new
format can't be read by app versions that don't support it, so an app switching over must run
both for a while (Commonveil's plan will say how).

## 6. Effects on independent implementations

A second implementation needs X25519, ML-KEM-768 (FIPS 203), Ed25519, ML-DSA-65 (FIPS 204),
HKDF-SHA-256, HMAC-SHA-256 and AES-256-GCM, all widely available, plus the canonical JSON of
CVP-002. The vectors pin every derivation. Messages are JSON; sizes are listed in CVP-016.

## 7. Alternatives considered

- **MLS (RFC 9420)** for everything. Better for very large groups and well reviewed, but there
  is no standard post-quantum MLS ciphersuite yet and no small JavaScript implementation fit to
  vendor. Worth revisiting for groups once there is.
- **Signal's libsignal** directly. Its PQXDH and SPQR are reviewed, but it is native code with a
  heavy build, which doesn't fit the platforms Commonveil runs on today.
- **Keep the account-wide envelope and only drop the classical fallback.** Simple, but still no
  forward secrecy.
- **ML-DSA-65 on every group message.** Rejected for now on size (3.3 KB per message); can be
  added as a later version if reviewers want it.

## 8. Testing and migration

`test/session.test.mjs`: sessions both ways over many ratchet steps; out-of-order and late
messages; replay, tampering and downgrade refused with state unchanged; untrusted account keys
and swapped prekeys refused; one-time and last-resort prekeys; device-list rollback; fan-out to
several devices; groups with rekeying; linking and history transfer with tampered chunks
refused; vectors. The guards for downgrade, replay and group signatures were each removed in turn
to confirm a test fails without them.

Migration for apps is out of scope here. Commonveil's switch will be its own pull request with a
migration plan (dual-format period, device re-registration, history).

## 9. Implementation evidence

`src/session/` in Secure Net 0.4.0; `examples/two-party.mjs` runs two people, three devices, a
group and a new device through a relay that keeps everything, and finds no plaintext in it.
X25519, HKDF, HMAC and AES-GCM vectors agree with Node's built-in crypto.

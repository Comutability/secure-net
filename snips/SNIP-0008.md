# SNIP-0008: Brand-neutral Secure Net discovery and interoperable transport

| | |
| --- | --- |
| Status | Draft for public community and independent security review, not adopted |
| Author | AI-assisted technical draft at the founding steward's request; human proposer, reviewers and decision still to be recorded |
| Created | 2026-11-24 |
| Affected specification | CVP-005, CVP-008, CVP-015, CVP-017 and CVP-019 |
| Breaking | Proposed as additive discovery first; any signature domain change is breaking and requires a separate versioned migration |

## 1. Problem

Secure Net is an independent community-led protocol. Commonveil is its
first adopter, not its owner or a compulsory network gateway. However,
historical compatibility identifiers inherited from the original
Commonveil federation implementation still appear in the reference
CVP-005 wire code: a Commonveil-named well-known site document, a
Commonveil-specific protocol name and a Commonveil-derived signed-request
domain label. A developer building a different app may mistakenly infer
that Secure Net requires Commonveil registration or Commonveil servers.

This creates developer confusion and potential security risk if
implementers rename fields or signed bytes ad hoc, assuming these are
only brand strings. They are protocol inputs and cannot be silently
changed without breaking authentication.

## 2. Proposed change, not yet normative

Propose an independent Secure Net site discovery alias at
/.well-known/secure-net, with a versioned protocol identity
identifying Secure Net, an exact authenticated site origin, verified
site keys and explicitly advertised feature and endpoint paths.
A site would continue serving the historical well-known URL during a
documented transition. The alias MUST NOT provide new transfer authority,
override an existing actor's pinned key history, or bypass normal
CVP-005/015 authentication.

The alias is a **discovery mechanism**, not a new central relay.
Each compatible site may operate its own inbox/outbox/deliver services.
Any site should be able to support multiple independent applications
and operator domains, subject to its own privacy, moderation and hosting
policies. A protocol-compliant client MUST NOT require Commonveil login.

A separate future signature-domain version should use a brand-neutral,
domain-separated constant such as secure-net/request/v2 with an
independently reviewed signing transcript and an explicit negotiation
rule. This proposal does NOT currently define that future byte-exact
transcript; it must be developed, vectorised, peer-reviewed and approved
before anyone deploys a new signature version. No unsolicited fallback
from a previously pinned newer signed profile to weaker legacy rules
is allowed.

All new sites must advertise only fully implemented CVP capabilities.
Discovery alone does not make a site an encrypted delivery relay, and
historical Commonveil version 1 inbox/act routes cannot masquerade as
CVP-019 outbox/deliver/mailbox.

## 3. Benefits and intended uses

Any organisation can publish Secure Net compatibility on its own
domain and connect a website, mobile app, desktop client or self-hosted
service to other compatible sites. Commonveil remains the first app,
not a privileged client. A standalone relay operator can implement
the published CVP-005, CVP-015 and CVP-019 services without distributing
Commonveil.

## 4. Security and privacy

The alias must be bound to the requested HTTPS hostname and the same
independently verified site keys. Clients must reject off-origin URLs,
DNS rebinding, private-address SSRF, mismatched advertised hosts,
malicious redirects, replay, tampering, unsigned discovery documents
where authentication is required, and silent downgrade.

Signed actor key chains are still verified independently on recipient
devices. Relay hosts cannot read direct messages; they still see
recipient and traffic metadata. A protocol alias does not grant access
to accounts, keys, inboxes or migrated identities.

## 5. Compatibility

The first phase is additive: old implementations continue using the
existing, pinned site document and signature transcript unchanged.
New implementations may try an independently validated Secure Net
discovery alias, but MUST reject conflicting keys or features and
must preserve a higher-security previously pinned profile. Exact
fallback rules and their security review are required before adoption.

Any later request signing version requires a separately versioned
wire protocol, migration plan and conformance vectors. Neither a
Commonveil release nor this draft unilaterally changes existing
signed bytes.

## 6. Effects on independent implementations

No Commonveil-specific code or credentials should be required.
Examples must use neutral application names and sites with separate
accounts and data stores. Alternative libraries are explicitly
allowed as long as their cryptographic and wire behaviour conforms
to the published specifications.

## 7. Alternatives considered

- Keep historical branding forever: mechanically compatible, but
  confusing for independent implementers.
- Change every historical endpoint and signature in one release:
  rejected due to breakage, first-contact trust and downgrade risk.
- Require a single Commonveil-operated relay: rejected because it
  undermines resilience, self-hosting and protocol independence.

## 8. Testing and migration requirements

- Byte-exact discovery, canonical encoding, request signing and
  authentication vectors for legacy and proposed independent versions.
- At least two independent site implementations and two application
  frontends, using different repositories and backends, exchanging
  encrypted CVP-019 traffic in both directions over actual HTTP.
- Full CVP-015 post-quantum sealed relay, wrong-key, replay, downgrade,
  site rotation, bad host, malicious proxy, queue expiry and retry tests.
- A staged rollout retaining old routes and a clear rollback plan, not
  silent replacement.
- Independent human cryptography/security review before enabling a
  new wire transcript or advertising production interoperability.

## 9. Implementation evidence

The existing Secure Net Rust reference uses independent CVP-019
in-memory sites and clients. The third_party_apps integration test
models distinct AuroraChat and LanternNotes frontends communicating
across simulated sites, with both encrypted messages and privacy
checks. It **does not** establish independent third-party HTTP or
encrypted relay conformance. No new discovery alias or signature
version is implemented by this SNIP.

## 10. Reviewers and decision

**Open for community comment.** No human security review,
technical steering committee decision, ratification or production
deployment has occurred. Community contributors should review the
discovery and signature downgrade threat model before implementation.

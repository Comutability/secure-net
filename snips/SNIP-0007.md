# SNIP-0007: Sovereign identity, private account migration and portable mail

## 1. Problem

A person's Commonveil account is not yet a portable protocol-level account. A self-hosted Commonveil identity is currently anchored to a site-specific username, site-specific sessions and an Ed25519-derived owner key, while the experimental Secure Net actor uses hybrid Ed25519 + ML-DSA-65 signing. The actor specification describes an identity move, but does not make all private history, contacts, incoming direct messages, attachments, recovery, device state and routing portable. The existing JSON data download is readable plaintext and cannot be imported as a live account.

The goal is the ability to move to another compatible self-hosted Commonveil instance without changing the person's cryptographic identity or trusting either instance with decryption secrets. Secure Net remains a separate protocol and acts as the interoperable inbox, outbox and transport between instances; Commonveil is one possible client and host.

## 2. Identity model

- **Permanent identifier**: CVP-017 actor id derived from a hybrid Ed25519 + ML-DSA-65 public account key, independent of hostname. Use the existing actor and signature formats; do not invent a second competing id.
- **Changeable handle**: `@name@site` is a routing alias, not the actor's authority or id. Display actor id/safety number when a handle changes. Other clients pin actor id and highest signed sequence seen.
- **Owner control**: the account signing secret remains device-owned; sites may hold encrypted backups but MUST NOT have the keys to decrypt them. Publish device addition/removal and key rotation as hybrid-signed, monotonic, replay-resistant account updates.
- **Account continuity**: if a current Commonveil account only has the classical owner proof, its owner must explicitly authorise the binding to the new post-quantum actor key. This must occur from a device able to prove ownership. A site cannot silently manufacture a new actor or certify migration for a user.
- **Recovery**: recovery secrets are client-side and independently backed up. Restoration MUST authenticate a new device and MUST NOT automatically retrieve forward-secret history which the previous device cannot decrypt. Passkeys are site- or relying-party-bound and must be re-enrolled at the destination.
- **Privacy**: signing a fresh challenge with a hybrid key proves possession without disclosing the private key. This is **not** a general zero-knowledge proof. The protocol MUST NOT advertise `zkp` or `quantum-resistant ZKP` as implemented unless an independently reviewed proof system and a precise statement, witness, verifier and threat model have been specified and tested.

## 3. Transfer format, wholly client encrypted

Define a future versioned `cvp.account-transfer` feature, opt-in and disabled until interoperability tests and review pass.

The exporting client assembles a streaming, authenticated, client-encrypted archive whose unencrypted envelope contains only version, algorithm suite, nonce/sequence information, random transfer id, expiry and a cryptographic commitment to the actor id. It MUST NOT contain contacts, usernames, message subjects, conversations or a recipient list in plaintext. A mandatory manifest inside the encrypted archive lists:

1. The signed actor document, its complete authenticated key/rotation chain, the pinned highest sequence, public repository head and records.
2. The local user's own contact and following graph, blocks, preferences, profiles, membership references and the exact provenance and consent scope of each object.
3. Encrypted message history and DM history, including stable message ids, ordering, attachment manifests, tombstones, edits, reactions and read states **where they are held and available**. Raw server ciphertext can be preserved but cannot be declared readable by the destination until the client can decrypt it.
4. User-owned session recovery material only when the user has explicitly authorised a protected device-to-device history handover; never export a live session secret into an unsealed archive.
5. Integrity-checked attachment blobs with encrypted contents, sizes and authenticated hashes, resumed in chunks.
6. Migration state: old host, new host, epoch, signed sequence, last delivered cursor, acknowledgement cursor, last known device list, expected item counts and failures.

Encrypt on the sending device. Derive a high-entropy archive encryption key locally; wrap it to the user's new authorised device using a hybrid X25519 + ML-KEM-768 KEM, or using a separately authenticated recovery mechanism with memory-hard password hardening and a strong, user-confirmed secret. Use domain-separated AEAD associated data covering archive version, actor id commitment, record category, part index and total parts. Each part gets a unique nonce. Verify the complete manifest and all chunks before making any destination state visible. Never log or upload secret keys, plaintext messages or recovery phrases in the relay.

A successful export MUST report which items were included, which could not be decrypted, which were excluded by retention/expiry, and which attachments remain pending. It must not claim a complete history when source devices or messages are unavailable.

## 4. Migration as a two-phase operation

1. **Prepare**: discover destination capabilities, self-hosting and policy. Reject incompatible cryptographic suites, revoked hosts, weaker-than-pinned transport, missing storage capacity or an inability to verify the hybrid actor. The destination presents a fresh bound challenge with actor id, destination origin, nonce, expiry and transfer id.
2. **Prove**: the client signs the challenge with its current actor key on an authorised device. Destination checks both Ed25519 and ML-DSA-65, monotonic sequence, revocation history, and its own replay cache, before reserving the id.
3. **Transfer**: client streams encrypted chunks to the destination; resume by hash and cursor. Destination sees no private contents. An independent destination client decrypts, validates, de-duplicates and re-encrypts content for its own encrypted store. No migration event may reassign a recipient's keys or silently change a group membership.
4. **Cutover**: publish a higher-sequence hybrid-signed actor document pointing to the new host. Both hosts independently verify it; old host serves a signed `moved` pointer for the actor id and former handle. Discovery must verify signatures, prevent downgrade and reject rollback.
5. **Relay drain**: old site's inbox/outbox forwards only already-encrypted pending envelopes to the new host, de-duplicates by stable envelope id, bounds retry/expiry, and acknowledges deliveries only after durable destination acceptance. New inbound messages must route to the new host, including messages sent using previously cached addresses.
6. **Commit**: client compares source and destination counts, manifests and cursors, displays gaps, and explicitly confirms cutover. Only then optionally revoke old sessions and schedule old-site account deletion, with an independently confirmed grace period. Do not delete the source account while a transfer is incomplete.
7. **Recovery**: if source host is offline, the client may use its independently held signed actor chain, encrypted local archive and another verifiable relay to move without source approval. This does **not** recover data which exists only on the unavailable host. Receivers must use highest-sequence pinning or independent transparency/witness proofs to resist equivocation and first-contact substitution.

Atomic cutover across independent sites is not feasible without coordination. The UI must describe the interval as a recoverable, logged two-phase move, not guarantee a global instant transaction.

## 5. Secure Net as independent inbox, outbox and relay

- Secure Net owns public protocol envelopes, discovery, mailbox cursors, delivery receipts, retry and authenticated site-to-site relay semantics. Commonveil does not introduce private, Commonveil-only federation routes for portable mail.
- Client -> **Secure Net outbox** -> signed, hybrid PQ-sealed site transport -> **Secure Net inbox** -> recipient's authorised client. Client-to-client encryption remains inside the sealed relay; the two site servers cannot decrypt direct or private group content.
- Follow CVP-019's direct, audience and public envelope modes, CVP-015's hybrid relay and CVP-016's forward-secret sessions. Do not downgrade to classical-only crypto when a previously pinned actor or site used hybrid keys.
- Delivery MUST handle device fan-out, at-least-once delivery with idempotent ids, queue limits, rate controls, authenticated acknowledgements, expiry, spam prevention without content inspection, and bounded retries.
- Relays can observe timing, rough sizes, ingress/egress network addresses and routing destinations, even while contents remain unreadable. The endpoint operator may also learn its local account's contact graph through membership and delivery patterns. Do not describe this as metadata-free, anonymous or absolute zero knowledge.
- Device-specific history keys require an explicit recipient-authorised transfer. Never weaken forward secrecy to make history portable.

## 6. What moves, and what requires permission

Portable by default: actor identity, key history, own public repository, local address book, settings, owned private content where ciphertext and decryption capability are available.

Conditional: DM history only available to the exporting user and their authorised device; attachments subject to retention and source availability; groups/servers according to their hosting and moderation policy; other people's profiles only to the extent explicitly permitted. Admin rights, bans, subscriptions, host-owned communities, third-party encrypted group secrets, and content deleted by expiry are **not** automatically transferable. Do not promise they are.

## 7. Verification and release gates

Before declaring production readiness:

- Cross-instance test with two independently hosted Rust servers; hosted Base44 compatibility assessed independently.
- Verify a stable actor id across repeated moves A -> B -> C, signed sequence continuity, replay and rollback rejection, hostile old/new servers, dropped/reordered/duplicated chunks, transfer resume and power loss.
- Reconcile conversation and attachment counts; explicitly test missing and undecryptable history, blocked accounts, deleted messages, group membership changes and pending mailbox delivery during cutover.
- Fuzz archive parsing, bound maximum sizes, reject malformed crypto suites, test nonce uniqueness and no plaintext in logs, traces, server records or push notifications.
- Run cryptographic test vectors for ML-DSA-65, ML-KEM-768 and the existing hybrid suites; independent external cryptographic and privacy review required for production claims.
- Publish migration recovery instructions and a clear user-facing rollback path; keep all new functionality opt-in and labelled experimental until then.

## 8. Rollout proposal

1. **Protocol**: adopt normative CVP-006 archive format plus additions to CVP-017/019, publish feature negotiation, conformance vectors and a test relay.
2. **Commonveil client**: display a stable actor id and safety number, offer a separately encrypted portable export and a validated read-only import preview. Clearly distinguish existing plaintext GDPR export from a migration archive.
3. **Self-hosted Commonveil server**: destination challenge, transfer staging, atomic per-record import, redirect/moved lookup and relay drain, all with tests and deterministic error codes.
4. **Cross-site move**: opt-in cutover UI with explicit reconciliation and rollback; test with multiple hosts before production release.
5. **Privacy proofs**: separately propose precisely scoped, formally specified ZK credentials only after choosing a secure post-quantum proof construction and obtaining qualified review.

## 9. Compatibility and governance

This SNIP is a design proposal, **not a claim of implementation**. Existing accounts and DM ciphertext remain untouched. The future wire format must use explicit versions and negotiated capabilities. A reviewer must establish how migration, user-controlled erasure and legally required retention interact with self-hosted operator duties. Human maintainers and the community approve the change through the Secure Net process.

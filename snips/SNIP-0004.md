## 1. Problem

The protocol has grown quickly, and the rules that let it keep growing safely were missing:

- **No rules for change.** Nothing said what makes a change compatible or breaking, how parts,
  features and releases are versioned relative to each other, or how anything is retired.
- **Shared names lived only in the code.** About 20 record kinds, 14 ledger events, extension
  permissions, endpoints, headers, 5 algorithm suites and around 40 domain-separation labels were
  defined only where the code happened to use them. Nothing stopped a name being reused with a
  different meaning, or a label changing silently.
- **No way to claim conformance.** Someone writing a second implementation had no profiles to aim
  for, no vectors for the encoding everything else rests on, and no way to say what they support.
- **Documents and code could drift.** The spec index was hand-maintained, six implemented parts
  had no document, and parts had no common structure.

## 2. Proposed change

- **CVP-000**: normative language; what is normative and in what order of authority (documents and
  registries, then vectors, then code); part structure and statuses; four kinds of version
  (release, part, feature, label) and when each changes; receiver rules for unknown data; what
  counts as additive or breaking; a deprecation lifecycle (Active, Deprecated, Legacy, Removed,
  with at least two minor releases and six months); registry rules and naming; vector
  requirements; errata; security fixes; writing style.
- **Registries** (`spec/registry.json`, readable as `spec/REGISTRIES.md`): parts, features, record
  kinds, ledger events and capabilities, extension permissions, consent actions, vote methods,
  algorithm suites, labels, protocol identifiers, endpoints, HTTP headers, conformance profiles.
- **CVP-010**: seven conformance profiles, what conforming means, and a JSON conformance statement;
  the reference implementation publishes its own (`secure-net-conformance.json`).
- **CVP-002** written down as a part document, with language-neutral vectors for canonical JSON and
  signed records (classical and quantum-resistant), including records that must be refused.
- **A part template**, and the existing part documents brought into the standard format.
- **`scripts/standards.mjs`**, run in CI and by `npm test`: fails if any name the code uses is
  unregistered (or registered but absent), if the feature list, suites, endpoints or versions
  differ, if a part document's status or version differs from the registry or a required section
  is missing, if the conformance statement is untrue, or if a generated file is stale.
- The session module now refuses to derive keys under any label purpose not in its registered
  list, so a new label can't be introduced without registering it.

Secure Net 0.4.1 (patch: nothing on the wire changes).

## 3. Benefits and intended uses

Contributors know how to make a change and what it will cost; maintainers can tell additive from
breaking at a glance; independent developers get a stable target, vectors to test against and a
way to say what they support; and the standard can't quietly fall out of step with the code.

## 4. Security and privacy

No cryptographic behaviour changes. The framework adds three security rules worth reviewers'
attention: a label's meaning never changes (4.4); a receiver refuses unknown values wherever
accepting them would grant something (5.1); and insecure things can be removed without waiting
for the deprecation period (6), but never without human security review (11). The CVP-002 text
adds one normative rule the code already follows in practice: receivers keep unknown body members
and verify over the body as received.

## 5. Compatibility

Additive and editorial only. No record, message, label or feature changes. Statuses in the
registry are set honestly: every part is Draft, because none has yet been through Technical
Review under GOVERNANCE.md.

## 6. Effects on independent implementations

They gain a definition of the encoding every other part depends on (CVP-002), vectors for it, a
list of every name they must use, and profiles to aim for.

## 7. Alternatives considered

- **Adopt IETF RFC format.** Heavier than this project needs now; CVP-000 borrows its key words
  and its habits (normative versus informative, security sections) without the process.
- **Registries as Markdown only.** Easier to read, impossible to check automatically. JSON is the
  source and Markdown is generated from it.
- **Generate the registry from the code.** That would make the code the standard. The registry is
  written by hand and the code is checked against it, so changing a name is a deliberate act.

## 8. Testing and migration

`test/standards.test.mjs` runs the checker and the vectors. The checker was run against ten kinds
of deliberate drift, one at a time, and named the problem each time: an unregistered record kind,
a changed feature version, a new label, a stale generated index, a part document whose status
differs from the registry, a missing required section, a changed endpoint, an untrue conformance
statement, an added extension permission, and a ledger event whose capability changed. No
migration is needed.

## 9. Implementation evidence

- `scripts/standards.mjs`, `scripts/vectors.mjs`, `spec/registry.json`, `spec/vectors/cvp-002-v1.json`.
- CVP-002's canonical vectors were reproduced by a separate canonical-JSON encoder written in
  Python from the text of CVP-002 alone. Python's default key sort gives a different answer on one
  case, so the vectors do catch that common mistake.
- The Ed25519 signature and both key ids were checked with Node's built-in crypto.

# SNIP-0009: Publishing the Secure Net standard

| | |
| --- | --- |
| Status | Draft |
| Author | Michael J Burgess (text prepared with AI assistance; he is the human responsible for it) |
| Created | 2026-11-27 |
| Specification | GOVERNANCE.md, CVP-000 (sections 3, 4 and a new section on publication), every part in `spec/` |
| Breaking | No. Nothing here changes what two implementations must agree on |

## 1. Problem

Secure Net's specifications live in a Git repository and change with each merge. That is fine
for the people writing them, but someone deciding whether to build on the protocol needs to
know four things the repository doesn't yet tell them:

- **Which text is the standard.** Today there is only the latest commit. There is no fixed,
  citable edition, and nothing says which version of a part a conformance claim refers to.
- **What they may do with it.** The repository is AGPL-3.0-only. That suits the reference code,
  but applied to the specification text it may put off implementers who can't take on copyleft
  terms, which works against an open protocol. Nothing is said about patents.
- **How long they have to comment.** GOVERNANCE.md names the review stages but sets no minimum
  periods, so a change could move from Draft to Accepted in a day.
- **Where to find it.** comutability.org shows the protocol, but has no permanent addresses for
  parts or editions.

Every part is currently Draft and no human reviewer has examined any of them. This proposal
doesn't change that. It sets how the standard is published so that, as parts are reviewed, what
is published says honestly where each one stands.

## 2. Proposed change

### 2.1 Three kinds of published text

| Kind | What it is | Where |
| --- | --- | --- |
| **Editor's draft** | The current text on `main`. Changes with every merge. Never cited in a conformance claim. | GitHub, and `comutability.org/standards/secure-net/draft/` |
| **Working draft** | A snapshot taken at a Secure Net release, containing parts of any status. | `comutability.org/standards/secure-net/<release>/` |
| **Standard edition** | A snapshot taken at a release in which every part of the Core profile (CVP-010) is Accepted or Stable. Named after the release, for example "Secure Net Standard 1.0". | The same address pattern, marked as an edition |

Each published page shows, at the top and in words rather than colour alone: the part's status
(CVP-000 3.2), its part version, the release it belongs to, the date it was published, and
whether it may be deployed ("Experimental: never the only option between sites" for Draft and
Proposed parts).

### 2.2 Permanent addresses

- `comutability.org/standards/secure-net/<release>/cvp-NNN` is fixed once published. Its text is
  never edited afterwards. Errata (CVP-000 section 10) are listed on a separate errata page linked
  from it.
- `comutability.org/standards/secure-net/latest/cvp-NNN` points to the newest published release.
- Each snapshot records the release's `secure-net.manifest.json` hash, so anyone can check that
  the published text matches the tagged source.
- A withdrawn part's pages stay up, marked Withdrawn, so that old references still resolve.

### 2.3 Minimum review periods

A SNIP that changes what implementations must agree on moves through these stages, with the
minimum time at each counted from when it is announced (on GitHub, on comutability.org, and in
the SNIP forum on The Agora):

| Stage | Minimum | What must happen before it ends |
| --- | --- | --- |
| Public Review | 30 days | Anyone may comment. Every substantive comment gets a written answer. |
| Technical Review | 14 days | A reference implementation and tests exist; reviewers other than the author have examined it. For security-sensitive changes (GOVERNANCE.md), a named, qualified human security reviewer has signed off. |
| Last Call | 14 days | The final text is frozen apart from editorial fixes. Then the TSC records its decision. |

Editorial changes and errata need no SNIP. Security fixes follow CVP-000 section 11: they may be
fixed privately first and published with an advisory, but still get human security review.

A part reaches **Stable** only when at least two implementations, at least one of them not
written or maintained by Comutability, pass its vectors and say so in a published conformance
statement.

### 2.4 Licences

- **Specification text** (`spec/`, `snips/`, `GOVERNANCE.md` and the protocol guide in
  `docs/guide/`): Creative Commons Attribution 4.0 International (CC BY 4.0). Anyone may copy,
  translate, adapt and republish it with credit.
- **Test vectors and registries** (`spec/vectors/`, `spec/registry.json`): CC0 1.0, so they can be
  copied into any test suite without conditions.
- **Code**: unchanged, AGPL-3.0-only.
- **Patents**: everyone who contributes to specification text agrees that, for any patent claim
  they hold that an implementation of an Accepted or Stable part would necessarily infringe, they
  grant a royalty-free licence to implement it (the Open Web Foundation Final Specification
  Agreement 1.0, or an equivalent the reviewing lawyer prefers). Contributors confirm this when
  their first specification change is merged.
- **Names**: "Secure Net" and "Comutability" are not licensed by any of the above. An
  implementation may say it "implements Secure Net <release>, <profile>" when its conformance
  statement (CVP-010) supports that.

This is a licence change, so GOVERNANCE.md applies in full: it needs legal review, the agreement
of everyone who holds rights in the specification text as it stands, and recorded human approval.
Rights already granted under AGPL-3.0 are not withdrawn. Until all of that is done, the text stays
AGPL-3.0-only.

### 2.5 The standards index

`comutability.org/standards/` lists every part, generated from `spec/registry.json` (as the spec
index already is), with its status, version, features and the SNIPs that changed it, and links to
each SNIP and its decision. It is regenerated on every release, so the site never claims a status
the registry doesn't.

## 3. Benefits and intended uses

Implementers can cite a fixed text, know what they may do with it, and know how long they have to
object to a change. The protocol can be adopted by projects that can't accept copyleft terms for a
specification, without weakening the code's licence.

## 4. Security and privacy

No effect on the protocol. Fixed snapshots with a recorded hash make it harder to slip an
unreviewed change into text people believe was reviewed. Minimum periods give security reviewers
time. The security-fix route is unchanged.

## 5. Compatibility

None: no wire format, label or rule changes.

## 6. Effects on independent implementations

They gain fixed texts to cite, an explicit patent licence, and a path to Stable that requires an
implementation other than Comutability's. Nothing here favours one implementation.

## 7. Alternatives considered

- **Keep the specification under AGPL-3.0.** Simplest, but copyleft on a specification is unusual
  and may stop some implementers from using or quoting it.
- **Apache-2.0 for the text.** Includes a patent grant, but is written for software and fits prose
  awkwardly.
- **W3C Software and Document Licence plus the W3C Patent Policy.** Well understood, but written
  around W3C membership.
- **No minimum periods, leaving it to the TSC's judgement.** Faster, but gives outsiders no
  assurance they will be heard.

## 8. Testing and migration

- `cargo run -p secure-net-tools -- standards` gains a check that each part's header has a status
  and version that match the registry.
- The website build checks that every published snapshot's text matches the manifest hash of its
  tag.
- Migration: once Accepted, licence notices are added to `spec/`, `snips/` and `docs/guide/`, a
  `CONTRIBUTING.md` records the patent commitment, and the first working draft is published at the
  next Secure Net release.

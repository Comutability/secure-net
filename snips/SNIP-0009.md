# SNIP-0009: Publishing the Secure Net standard

| | |
| --- | --- |
| Status | Draft |
| Author | Michael J Burgess (text prepared with AI assistance; he is the human responsible for it) |
| Created | 2026-11-27 |
| Specification | GOVERNANCE.md (the proposal lifecycle, and "Licence and contributions"); SNIP-TEMPLATE.md (status list); CVP-000 (3.2 Stable, a new section 13 Publication; Version 1 to 2); README.md and the licence files |
| Breaking | No. Nothing here changes what two implementations must agree on |

## 1. Problem

Secure Net's specifications live in a Git repository and change with each merge. That is fine
for the people writing them, but someone deciding whether to build on the protocol needs to
know four things the repository doesn't yet tell them:

- **Which text is the standard.** Today there is only the latest commit. There is no fixed,
  citable edition, and nothing says which text a conformance claim refers to.
- **What they may do with it.** The repository is AGPL-3.0-only. That suits the reference code,
  but applied to the specification text it may put off implementers who can't take on copyleft
  terms, which works against an open protocol. Nothing is said about patents.
- **How long they have to comment.** GOVERNANCE.md names the review stages but sets no minimum
  periods, so a change could move from Draft to Accepted in a day.
- **Where to find it.** comutability.org shows the protocol, but has no permanent addresses for
  parts or editions.

Every part is currently Draft and no human reviewer has examined any of them. This proposal
doesn't change that. It sets how the standard is published so that, as parts are reviewed, what
is published says honestly where each one stands.

## 2. Proposed change

### 2.1 Three kinds of published text

| Kind | What it is | Where |
| --- | --- | --- |
| **Editor's draft** | The current text on `main`. Changes with every merge. Never cited in a conformance claim. | GitHub, and `comutability.org/standards/secure-net/draft/` |
| **Working draft** | A snapshot taken at a Secure Net release, containing parts of any status. | `comutability.org/standards/secure-net/<release>/` |
| **Standard edition** | A snapshot taken at a release in which CVP-000, CVP-010 and every part of the `core` profile (CVP-010) are Accepted or Stable. Named after the release, for example "Secure Net Standard 1.0". | The same address pattern, marked as an edition |

A standard edition contains only parts that are Accepted or Stable. A part marked "Accepted
(provisional)" under SNIP-0010's founder phase may be included, and is marked as provisional in
the edition. Parts below Accepted at that
release are listed in an annex headed "Not part of this edition", with their status, and are not
covered by a conformance claim against the edition.

Each published page has two parts:

- **The frozen text**: the part exactly as released, including the status it had at that release
  (CVP-000 3.2), its part version, the release and the publication date. It never changes.
- **A status banner** above it, kept by the site outside the frozen text. It says what may be
  done with **the version on this page**, from that version's own status (as released, or as
  changed since):

  | That version's status | Banner says |
  | --- | --- |
  | Accepted or Stable | May be deployed |
  | Deprecated (at release or since) | Receive only (CVP-000 section 6) |
  | Withdrawn | No longer part of the protocol: don't use |
  | Draft or Proposed | Experimental: never the only option between sites |

  Separately, it gives the part's current status and links to later versions and errata, so a
  later Accepted version never makes an earlier Draft page look deployable. Statuses are shown in
  words, not colour alone. The banner is regenerated whenever the registry changes on `main`, and is the
  only part of a published page that changes.

### 2.2 Permanent addresses

- `comutability.org/standards/secure-net/<release>/cvp-NNN` is fixed once published. Its text is
  never edited afterwards. Errata (CVP-000 section 10) are listed on a separate errata page linked
  from it.
- `.../latest/cvp-NNN` points to the newest **standard edition**; until there is one it says so and
  links to the newest working draft. `.../latest-draft/cvp-NNN` points to the newest working draft.
- Each page links to its Markdown source at the release tag on GitHub and shows the release's
  `secure-net.manifest.json` hash. The site is built from the tagged source, and the build checks
  that the source it rendered matches the manifest. (The hash identifies the source, not the
  rendered page; the source is what is normative.)
- A withdrawn part's pages stay up so that old references still resolve. "Withdrawn" appears in
  the status banner; the frozen text keeps the status it was released with.

### 2.3 Stages and minimum review periods

This adds **Last Call** to the lifecycle in GOVERNANCE.md and the template's status list:
Draft, Public Review, Technical Review, Last Call, Accepted or Rejected, Implemented, Released.
While a SNIP that changes a part is at Draft, Public Review or Technical Review, the **new
version** it proposes is Draft; once Technical Review is complete and Last Call starts, that version
is Proposed (CVP-000 3.2: "through Technical Review, decision pending"). A version already Accepted
or Stable keeps its status while a change to it is under review. The registry records the proposed
version separately, and the published version's status changes only with a decision.

These minimum periods apply to **every** SNIP that needs a decision, including licence and
governance proposals such as this one and SNIP-0010:

| Stage | Minimum | What must happen before it ends |
| --- | --- | --- |
| Public Review | 30 days | Anyone may comment. Every comment that asks for a change or raises a problem gets a written answer in the SNIP's discussion. |
| Technical Review | 14 days | For a protocol change: a reference implementation and tests exist, and reviewers other than the author have examined them. For a security-sensitive change (GOVERNANCE.md): a named, qualified human security reviewer has signed off. For other SNIPs: reviewers other than the author have examined the text. |
| Last Call | 14 days | The text is frozen apart from editorial fixes. Then the TSC records its decision. |

- Each period starts when the last of the three announcements is made: on the pull request, on
  comutability.org, and in the SNIP forum on The Agora. The date is recorded in the SNIP.
- A change to the proposal's substance during a stage restarts that stage's period.
- Whether a comment was answered is for the commenter to dispute: an unanswered comment is a
  ground of appeal (SNIP-0010).

Editorial changes and errata need no SNIP. Security fixes follow CVP-000 section 11: they may be
fixed privately first and published with an advisory, but still get human security review.

### 2.4 Stable

This replaces the Stable row of CVP-000 3.2. A part is **Stable** when it is Accepted and:

- for a part with test vectors: at least two implementations pass all its vectors, and at least
  one of them is independent (SNIP-0010 2.2), each saying so in a published conformance statement
  (CVP-010);
- for a part without vectors: the same, with an implementation-independent conformance test suite
  for it once one exists (CVP-010 lists such a suite as still to be written);
- a part with neither (CVP-000, CVP-010, informational parts) can be Accepted but not Stable.

"Independent" is as defined in SNIP-0010 2.2. This proposal depends on that definition: if
SNIP-0010 isn't adopted, this proposal must define the term itself before Last Call.

### 2.5 Licences

| Material | Licence |
| --- | --- |
| Specification prose: `spec/*.md` except as below, `snips/`, `GOVERNANCE.md`, `docs/guide/` | Creative Commons Attribution 4.0 International (CC BY 4.0) |
| Test vectors and registries: `spec/vectors/`, `spec/registry.json`, and files generated from them (`spec/REGISTRIES.md`, the generated index in `spec/README.md`) | CC0 1.0 |
| Code samples inside specification text | Also available under CC0 1.0, so they can be pasted into software |
| Code | Unchanged: AGPL-3.0-only |

CC BY 4.0 lets anyone copy, translate, adapt and republish the text, including commercially,
provided they give credit, link to the licence and say if they changed it.

**Patents.** Neither CC BY 4.0 nor CC0 1.0 grants patent or trademark rights, so:

- before their first change to specification text is merged, each contributor agrees to the Open
  Web Foundation Contributor License Agreement 1.0 (OWF CLA), copyright and patent terms;
- at each standard edition, Comutability, and every contributor who agrees, make the Open Web
  Foundation Final Specification Agreement 1.0 (OWFa) commitment for that edition.

Legal review also decides who can give the edition commitment: whether Comutability is a legal
person able to make it, and if not, who makes it on its behalf. The lawyer reviewing this proposal
confirms these instruments or names replacements before
Public Review ends. If any is replaced, the text of this proposal is changed to name it, and
Public Review restarts. Contributors are never asked to agree to an unnamed document.

**Names.** This proposal licenses no names. Whether "Secure Net" and "Comutability" are protected,
and how, is for legal review. An implementation may say it "implements Secure Net Standard
<edition>, <profile>" when its conformance statement supports that.

**Conditions.** This is a licence change, so GOVERNANCE.md applies in full. It takes effect only
after all three of:

1. legal review, which also establishes who holds rights in the existing text (much of it was
   prepared with AI assistance, and the law on copyright in such text, including section 9(3) of
   the UK Copyright, Designs and Patents Act 1988, is unsettled);
2. the agreement of everyone found to hold rights in it;
3. recorded human approval in the decision register.

Rights already granted under AGPL-3.0 are not withdrawn. Until all three are done, everything
stays AGPL-3.0-only.

### 2.6 The standards index

`comutability.org/standards/` lists every part, with its status, version, features and the SNIPs
that changed it, and links to each SNIP and its decision. It is generated from
`spec/registry.json`, as the index in `spec/README.md` already is (`secure-net-tools standards
--write`), and regenerated whenever the registry changes on `main`, so the site never claims a status the registry
doesn't.

### 2.7 CVP-000

CVP-000 gains section 13, "Publication", stating 2.1, 2.2 and 2.4 above, and its 3.2 Stable row is
replaced by 2.4. CVP-000 goes from Version 1 to Version 2 (CVP-000 4.2).

## 3. Benefits and intended uses

Implementers can cite a fixed text, know what they may do with it, and know how long they have to
object to a change. The protocol can be adopted by projects that can't accept copyleft terms for a
specification, without weakening the code's licence.

## 4. Security and privacy

No effect on the protocol. Fixed snapshots with a recorded hash make it harder to slip an
unreviewed change into text people believe was reviewed. Minimum periods give security reviewers
time. The security-fix route is unchanged.

## 5. Compatibility

None: no wire format, label or rule between implementations changes.

## 6. Effects on independent implementations

They gain fixed texts to cite, an explicit patent commitment, and a path to Stable that requires
an independent implementation. Nothing here favours one implementation.

## 7. Alternatives considered

- **Keep the specification under AGPL-3.0.** Simplest, but copyleft on a specification is unusual
  and may stop some implementers from using or quoting it.
- **Apache-2.0 for the text.** Includes a patent grant, but is written for software and fits prose
  awkwardly.
- **W3C Software and Document Licence plus the W3C Patent Policy.** Well understood, but written
  around W3C membership.
- **No minimum periods, leaving it to the TSC's judgement.** Faster, but gives outsiders no
  assurance they will be heard.

## 8. Testing and migration

- `secure-net-tools standards` already checks each part's header against the registry. It gains a
  check that a part marked Stable has two conformance statements, one of them from an independent
  implementation.
- The website build checks each snapshot's source against the manifest of its tag.
- Once accepted, and for 2.5 only once its three conditions are met:
  - `LICENSE-SPEC` (CC BY 4.0) and `LICENSE-CC0` are added, with a note in `LICENSE` saying which
    files each covers;
  - GOVERNANCE.md's "Licence and contributions" section and README.md's "Licence" section are
    updated;
  - `CONTRIBUTING.md` records the OWF CLA step;
  - GOVERNANCE.md and SNIP-TEMPLATE.md gain Last Call;
  - CVP-000 Version 2 is written;
  - the first working draft is published at the next Secure Net release.
